# Smart Home

Проект мобильной системы для подключения, управления и мониторинга устройств умного дома.

## Состав проекта

| Каталог | Назначение | Текущее состояние |
|---|---|---|
| `app` | Android-приложение на Kotlin и Jetpack Compose | Есть стартовый экран авторизации; интеграция с backend ещё не реализована |
| `auth` | Сервис аутентификации пользователей | Spring Boot + Kotlin skeleton; бизнес-логика, persistence и API пока не реализованы |
| `api-smart-home` | API для групп устройств, устройств и real-time данных | Spring Boot + Kotlin skeleton; интеграция с MQTT, БД и real-time транспортом пока не реализована |
| `esp8266` | Пример прошивки устройства измерения температуры | PlatformIO/Arduino; чтение LM75A и вывод на TM1637, MQTT/Wi‑Fi/Web UI ещё не добавлены |
| `system-model` | База знаний Obsidian с описанием системы и схемой сервисов | `Описание.md` и `Сервисы.canvas` |

## Архитектура

Система разделена на четыре прикладных компонента и инфраструктуру:

```text
┌──────────────┐       HTTP/JSON        ┌──────────────────┐
│ Android app  │ ◄────────────────────► │ api-smart-home   │
└──────┬───────┘                        └───────┬──────────┘
       │ HTTP/JSON                              │
       ▼                                        │ MQTT subscribe/publish
┌──────────────┐                                ▼
│     auth     │                         ┌──────────────┐
└──────┬───────┘                         │ Mosquitto    │
       │                                  └──────┬───────┘
       ▼                                         │ MQTT
┌──────────────┐                                  ▼
│ Auth Postgres│                            ┌──────────┐
└──────────────┘                            │ ESP8266  │
       │                                    └──────────┘
       ▼
     Redis

api-smart-home ─────► Smart Home Postgres
```

### Ответственность компонентов

`auth` отвечает за регистрацию с подтверждением email-кодом, вход, выход, управление учётной записью и валидацию JWT. Redis предназначен для временных кодов подтверждения и отозванных токенов, а PostgreSQL — для постоянных учётных записей.

`api-smart-home` отвечает за изоляцию данных по пользователям, CRUD групп и устройств, приём телеметрии из MQTT, команды устройствам и публикацию изменений мобильному клиенту в реальном времени.

`app` является клиентом HTTP API и real-time канала. На текущем этапе в приложении есть Compose-экран авторизации; WebView для настройки ESP8266 пока отсутствует.

`esp8266` — тестовое устройство с датчиком LM75A и дисплеем TM1637. В целевой версии оно должно подключаться к Wi‑Fi и Mosquitto, публиковать телеметрию температуры и иметь локальную web-страницу настройки.

## Потоки данных

### Аутентификация

1. Приложение отправляет запрос регистрации в `auth`.
2. `auth` сохраняет email и хэш шестизначного кода в Redis и отправляет код на почту.
3. После подтверждения email пользователь сохраняется в Auth PostgreSQL.
4. При входе `auth` выдаёт JWT.
5. Другие сервисы проверяют JWT через endpoint `/validate` или общий механизм проверки подписи. Отозванные токены хранятся в Redis до окончания срока жизни.

### Телеметрия устройства

1. ESP8266 измеряет температуру.
2. Устройство публикует сообщение в Mosquitto по согласованному MQTT topic.
3. `api-smart-home` подписывается на topics устройств, проверяет принадлежность устройства пользователю и сохраняет актуальное состояние/историю.
4. Сервис передаёт изменение в мобильное приложение через WebSocket или Server-Sent Events.

### Команды устройству

1. Пользователь выполняет действие в приложении.
2. Приложение отправляет команду в `api-smart-home`.
3. Сервис проверяет права пользователя и публикует команду в MQTT topic устройства.
4. Устройство применяет команду и публикует подтверждение или новое состояние.

## API auth (проектируемый контракт)

По материалам базы знаний предусмотрены следующие операции:

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/reg` | Регистрация и отправка кода подтверждения |
| `POST` | `/auth/login` | Вход и выдача токена |
| `POST` | `/auth/logout` | Отзыв токена |
| `DELETE` | `/auth/login` | Удаление аккаунта |
| `PUT` | `/auth/login` | Обновление данных аккаунта |
| `POST` | `/validate` | Проверка токена |

Контракт необходимо дополнить форматами запросов и ответов, кодами ошибок, правилами refresh/access token и способом передачи токена.

## MQTT и Homie Convention

В базе знаний указано использование «Mosquitto MQTT (протокол Homie Convention)». Mosquitto — это MQTT-брокер, а Homie Convention — соглашение о структуре topics и служебных сообщений поверх MQTT. Это разные уровни и их следует явно разделять в документации и коде.

До реализации интеграции нужно зафиксировать:

- версию Homie Convention;
- уникальный `device_id` и правила его регистрации;
- topics устройства, node и property;
- payload и единицы измерения температуры;
- retained-сообщения, QoS и Last Will;
- ACL брокера и учётные данные устройств;
- формат команд и подтверждений.

Для первой версии рекомендуется использовать Homie для discovery/описания устройства, а внутри `api-smart-home` привести MQTT-события к собственному доменному формату. Это не позволит MQTT-топикам протечь во все слои backend и упростит замену прошивки или брокера.

## Real-time API

Для мобильного приложения рекомендуется WebSocket: он поддерживает двунаправленный обмен, что удобно для событий состояния и подтверждений команд. Минимальное событие должно содержать `eventId`, `deviceId`, `property`, `value`, `timestamp` и версию состояния.

Не следует открывать мобильному приложению прямой доступ к Mosquitto. MQTT должен оставаться внутренним транспортом между устройствами и `api-smart-home`; backend должен быть точкой авторизации и фильтрации событий.

## Локальный запуск

На момент подготовки README в репозитории нет docker-compose-файла, конфигурации окружений, описания переменных и полностью реализованных API. Поэтому команды ниже запускают только заготовки сервисов и прошивочный проект.

### Auth и API

Требуются JDK 21 и Maven:

```bash
cd auth
mvn spring-boot:run
```

```bash
cd api-smart-home
mvn spring-boot:run
```

Оба сервиса сейчас содержат Spring Boot entry point и тест-заготовку, но не имеют рабочего набора endpoint'ов.

### Android-приложение

Открыть каталог `app` в Android Studio и запустить конфигурацию `app` на эмуляторе или устройстве. Проект использует Kotlin, Jetpack Compose и Android SDK с `compileSdk`/`targetSdk` 37.

### ESP8266

Требуется PlatformIO:

```bash
cd esp8266
pio run
pio run --target upload
pio device monitor
```

Сейчас прошивка читает LM75A и выводит температуру в Serial и на TM1637. Настройки Wi‑Fi, MQTT и веб-конфигуратор в текущей реализации отсутствуют.

## Рекомендуемая структура разработки

Для backend рекомендуется разделить код на domain, application, infrastructure и web слои. MQTT-клиент и WebSocket-адаптер должны быть инфраструктурными адаптерами, а правила доступа к группам и устройствам — доменной/application-логикой. Схема данных должна содержать владельца группы и устройства, иначе нельзя надёжно обеспечить изоляцию пользователей.

Для real-time доставки стоит предусмотреть reconnect мобильного клиента, повторную подписку, heartbeat, ограничение размера очереди событий и восстановление актуального состояния после разрыва. WebSocket не заменяет initial REST-запрос: приложение должно сначала получить снимок состояния, затем подписаться на изменения.

## Архитектурные замечания

1. **Сервисы пока являются skeleton-проектами.** README описывает целевую архитектуру, но нельзя считать перечисленные endpoint'ы и интеграции реализованными до появления контроллеров, миграций, конфигурации и интеграционных тестов.
2. **Нужно разделить два PostgreSQL.** В схеме указаны Auth PostgreSQL и PostgreSQL умного дома. Для независимых сервисов предпочтительны отдельные базы или как минимум отдельные владельцы схем и учётные записи; `api-smart-home` не должен читать таблицы `auth` напрямую.
3. **Нужно определить модель авторизации между сервисами.** Валидация JWT должна быть единообразной: общая подпись с безопасным управлением ключами или introspection endpoint. Передача пользовательского ID без криптографической проверки недопустима.
4. **Название Mosquito следует исправить на Mosquitto.** Mosquitto — название брокера.
5. **Homie Convention нужно зафиксировать явно.** Сейчас это вопрос в заметке, а от него зависят discovery, topics и payload.
6. **ESP8266 нельзя считать доверенным клиентом.** MQTT credentials, ACL, TLS и provisioning нужно спроектировать до подключения устройств к общей сети.
7. **WebView для настройки ESP8266 — компромисс.** Для первого прототипа он допустим, но приложение должно проверять, что открывает ожидаемый локальный адрес, а конфигуратор не должен передавать секреты по незащищённому каналу в общей сети.
8. **Нужен единый репродуцируемый dev-стенд.** Следующим инфраструктурным шагом стоит добавить Docker Compose для Mosquitto, PostgreSQL (две базы или два сервиса), Redis и backend-сервисов, а также `.env.example` без секретов.
9. **В репозитории присутствуют build-артефакты.** Каталог `esp8266/.pio` и Android `build` лучше исключить из Git и удалить из истории/рабочего дерева только отдельным согласованным изменением; README их не изменяет.

## План ближайшей реализации

Сначала зафиксировать контракты auth и smart-home, модель данных и MQTT topics. Затем реализовать auth с миграциями и Redis, после чего добавить доменную модель групп и устройств. Далее подключить MQTT consumer/producer, REST и WebSocket, а затем интегрировать Android-клиент. В конце добавить Wi‑Fi provisioning, web-конфигуратор ESP8266, Homie discovery, ACL/TLS и end-to-end сценарий «устройство → брокер → API → приложение».
