# Мобильное приложение и устройство ESP8266: userflow и интерфейсы MVP

Документ описывает текущую реализацию проекта, а не целевую production-архитектуру. Пути и контракты сверены с кодом `app`, `auth`, `api-smart-home`, `docker-compose.yml` и `esp8266` на дату подготовки. Все IP-адреса, кроме адреса точки доступа ESP8266, являются примерами или значениями по умолчанию: фактический адрес зависит от сети и способа запуска.

## 1. Userflow мобильного приложения

### 1.1 Первый запуск, регистрация и вход

1. При старте `MainActivity` читает сохранённый токен через `SessionStore`. Если расшифровать его не удалось или токен отсутствует, приложение показывает экран входа/регистрации.
2. Пользователь вводит email и пароль. На форме регистрации требуется повторить пароль; клиент проверяет совпадение и минимальную длину в 10 символов. Сервер дополнительно проверяет формат email и длину пароля 10–72 символа.
3. При регистрации приложение вызывает `POST /auth/reg`. В Compose подтверждение включено: сервис создаёт временную запись, отправляет шестизначный код через настроенный SMTP и ждёт подтверждение. До ввода верного кода пользовательской записи в PostgreSQL нет. Код действует 10 минут по умолчанию, разрешено не более пяти попыток.
4. После сообщения об отправке кода форма показывает ввод email-кода. Подтверждение вызывает `POST /auth/confirm`; при успехе экран возвращается к входу. Пользователь вводит пароль и вызывает `POST /auth/login`.
5. Вне Compose возможно отключить confirmation (`REQUIRE_EMAIL_CONFIRMATION=false`) и создавать аккаунт сразу. При включённом confirmation нужно настроить SMTP; без почтового провайдера регистрация завершится ошибкой отправки.
6. После входа приложение получает JWT и сохраняет его зашифрованным AES-GCM в `SharedPreferences`; ключ шифрования создаётся/хранится в Android Keystore. Затем открывается экран «Мой дом». JWT при REST-запросах передаётся как `Authorization: Bearer <JWT>`.

### 1.2 Работа с группами и устройствами

1. Экран загружает группы через `GET /api/groups`. Если группы есть, выбирается первая (либо ранее выбранная, если она ещё существует), затем загружаются устройства выбранной группы через `GET /api/devices?groupId=<UUID>`.
2. «Добавить группу» открывает диалог; подтверждение вызывает `POST /api/groups` с JSON `{"name":"..."}`.
3. Для добавления устройства пользователь выбирает группу и вводит отображаемое имя и Homie device ID. ID должен соответствовать `[A-Za-z0-9_-]{1,64}` и совпасть с `HOMIE_DEVICE_ID` прошивки. Клиент вызывает `POST /api/groups/{groupId}/devices`.
4. Карточка показывает имя, Homie ID и последнюю сохранённую температуру. Если телеметрии ещё не было, показывается «Ожидаем данные устройства».
5. Устройство можно удалить кнопкой «Удалить» (`DELETE /api/devices/{deviceId}`). Endpoint удаления группы также существует, но в текущем Android UI кнопки удаления группы нет.
6. «Выйти» очищает локальную сессию. Важно: текущий callback выхода очищает токен на устройстве, но не вызывает серверный `POST /auth/logout`, поэтому этот JWT не отзывается на сервере до истечения срока действия.

### 1.3 Реальное время

После загрузки домашнего экрана клиент открывает WebSocket `ws://<host>:8082/ws/devices` (или `wss://...` при HTTPS) с заголовком handshake `Authorization: Bearer <JWT>`. Сервер проверяет JWT и привязывает соединение к владельцу устройств. ESP публикует температуру в MQTT; API сохраняет последнюю property value и отправляет владельцу JSON-событие типа `telemetry`. Android обновляет отображаемую температуру и периодически/при событии перезагружает список устройств.

WebSocket — поток только сервер→клиент; клиентские команды по WebSocket не отправляются. API имеет REST endpoint для MQTT-команды `target-temperature`, но текущая прошивка — только термометр: она не подписывается на `/set`, не исполняет команду. Поэтому для данного устройства команды не являются рабочей функцией.

## 2. Адреса, IP и порты

### 2.1 Мобильное приложение → backend

Значения задаются полями `AUTH_BASE_URL` и `API_BASE_URL` в `app/app/build.gradle.kts` либо переопределяются через локальный `gradle.properties`.

| Источник клиента | Auth HTTP | Smart-home HTTP | WebSocket |
|---|---|---|---|
| Android Emulator (default) | `http://10.0.2.2:8081` | `http://10.0.2.2:8082` | `ws://10.0.2.2:8082/ws/devices` |
| Физический телефон в той же LAN | `http://<LAN-IP-хоста>:8081` | `http://<LAN-IP-хоста>:8082` | `ws://<LAN-IP-хоста>:8082/ws/devices` |

`10.0.2.2` — специальный адрес Android Emulator для хостовой машины, а не IP Docker-контейнера. Для физического телефона укажите LAN IP компьютера, на котором опубликованы Compose-порты. В локальном MVP разрешён HTTP cleartext; для внешнего окружения необходим HTTPS/WSS. Не используйте `localhost` на телефоне: он указывает на само устройство.

Пример `gradle.properties`:

```properties
AUTH_BASE_URL=http://192.168.1.10:8081
API_BASE_URL=http://192.168.1.10:8082
```

### 2.2 Backend → инфраструктура внутри Docker Compose

Внутри Compose-сети контейнеры обращаются к DNS-именам сервисов и внутреннему порту контейнера; опубликованные порты нужны хосту и устройствам LAN.

| Инициатор | Получатель | Адрес в Compose | Порт | Назначение |
|---|---|---|---:|---|
| `auth` | `auth-db` | `auth-db:5432` | TCP 5432 | PostgreSQL базы `auth` |
| `auth` | `redis` | `redis:6379` | TCP 6379 | JWT revocation и временные registration records |
| `api-smart-home` | `home-db` | `home-db:5432` | TCP 5432 | PostgreSQL базы `smart_home` |
| `api-smart-home` | `mosquitto` | `mosquitto:1883` | TCP 1883 | MQTT publish/subscribe |
| Android/хост | `auth` | `localhost:<published>` или `<host-LAN-IP>:8081` | TCP 8081 | Auth REST |
| Android/хост | `api-smart-home` | `localhost:<published>` или `<host-LAN-IP>:8082` | TCP 8082 | Smart-home REST и WS |
| Внешнее устройство/host tools | `mosquitto` | `<host-LAN-IP>:1883` | TCP 1883 | MQTT в локальной dev-сети |

Compose публикует PostgreSQL также на хост как `5433:5432` (auth) и `5434:5432` (home); Redis — `6379:6379`; Mosquitto — `1883:1883`; backend — `8081:8081` и `8082:8082`. Не подставляйте хостовые порты `5433`/`5434` в JDBC URL из контейнеров — между контейнерами используется `5432`.

Секрет JWT должен быть одним и тем же у `auth` и `api-smart-home`, иначе один сервис не сможет проверить токены другого. Docker Compose получает значения из `.env` и поднимает контейнеры командой `docker compose up --build -d`. Mosquitto сейчас открыт без аутентификации и предназначен только для изолированного dev-стенда.

### 2.3 ESP8266 → Wi-Fi/MQTT

| Коммуникация | Адрес/порт | Примечание |
|---|---|---|
| ESP8266 → Wi-Fi router/AP | SSID и пароль из веб-конфигуратора | Устройство работает как Wi-Fi STA при успешном подключении |
| ESP8266 → MQTT broker | `<MQTT host>:<MQTT port>`; по умолчанию порт `1883` | Host задаётся вручную; обычно это LAN IP машины с Mosquitto, не `localhost` и не Compose DNS `mosquitto` |
| Телефон → setup AP ESP | SSID `SmartHome-Setup`, пароль `setup1234`, IP `192.168.4.1` | Открыть `http://192.168.4.1/` после подключения телефона к AP |
| Телефон → web-конфигуратор в домашней Wi-Fi | `http://<ESP-LAN-IP>/` | IP выводится в Serial при подключении; можно посмотреть в DHCP leases роутера |

Порт веб-конфигуратора — TCP 80, задаётся `ESP8266WebServer web(80)`. MQTT порт выбирается в форме; рекомендуемое значение — 1883. Никакой внешний облачный адрес или фиксированный IP брокера в прошивке не зашит.

## 3. Каталог HTTP/WS endpoint-ов

Адреса ниже — пути относительно base URL сервиса. JSON тела передаются как `Content-Type: application/json`. Где требуется Bearer JWT, это указано. Ответы ошибок Spring могут иметь стандартный формат Problem Detail; конкретные сообщения зависят от причины.

### 3.1 Auth service — `http://<host>:8081`

| Метод | Путь | Auth | Входные данные | Результат/назначение |
|---|---|---|---|---|
| `POST` | `/auth/reg` | Нет | `{"email":"user@example.com","password":"..."}` | По умолчанию Compose отправляет код подтверждения через SMTP и создаёт только временную запись; учётная запись появится после верного кода. SMTP должен быть настроен. При выключенном confirmation аккаунт создаётся сразу. |
| `POST` | `/auth/confirm` | Нет | `{"email":"...","code":"123456"}` | Проверяет email-код; при выключенном confirmation возвращает `404`. Код живёт 10 минут по умолчанию; после 5 неверных попыток новые попытки блокируются до истечения TTL. |
| `POST` | `/auth/login` | Нет | `{"email":"...","password":"..."}` | Возвращает `accessToken`, `tokenType`, `expiresIn` (по умолчанию TTL 3600 секунд). |
| `POST` | `/auth/logout` | Bearer JWT | Тело не требуется | Отзывает текущий токен через Redis до его истечения; возвращает `{"success":true}`. |
| `POST` | `/validate` | Bearer JWT | Тело не требуется | Проверяет подпись/срок/revocation; возвращает `valid`, `userId`, `email`, `expiresAt`. |
| `PUT` | `/auth/login` | Bearer JWT | Необязательные поля `email`, `password`; нужно передать хотя бы одно изменение | Обновляет email и/или пароль; текущий токен отзывается. |
| `DELETE` | `/auth/login` | Bearer JWT | Тело не требуется | Удаляет аккаунт и отзывает текущий токен; возвращает `{"success":true}`. |

### 3.2 Smart-home API — `http://<host>:8082`

Все REST endpoint-ы требуют `Authorization: Bearer <JWT>`. Группы и устройства изолированы по owner UUID в токене.

| Метод | Путь | Входные данные | Результат/назначение |
|---|---|---|---|
| `GET` | `/api/groups` | — | Массив групп текущего пользователя. |
| `POST` | `/api/groups` | `{"name":"Кухня"}` | Создать группу; `201 Created`. Имя непустое, максимум 120 символов. |
| `DELETE` | `/api/groups/{groupId}` | UUID в path | Удалить принадлежащую пользователю группу и связанные устройства; `204 No Content`, чужая/неизвестная группа — `404`. |
| `GET` | `/api/devices` | Необязательный query `groupId=<UUID>` | Устройства пользователя, при наличии фильтра — выбранной группы; свойства включают последние значения. |
| `POST` | `/api/groups/{groupId}/devices` | `{"name":"Термометр","homieDeviceId":"esp8266-temp-01"}` | Зарегистрировать устройство в группе; `201 Created`. ID допускает `[A-Za-z0-9_-]{1,64}`. |
| `DELETE` | `/api/devices/{deviceId}` | UUID в path | Удалить устройство владельца; `204 No Content`. |
| `POST` | `/api/devices/{deviceId}/commands` | `{"property":"target-temperature","value":"22.5"}` | Публикует команду в MQTT; `202 Accepted`. В текущем MVP разрешено только `target-temperature`, диапазон −40…125; firmware не реализует обработчик команды. |
| `GET` | `/ws/devices` (WebSocket upgrade) | Заголовок handshake `Authorization: Bearer <JWT>` | Подключает владельца к live-событиям. Сообщение: `{"type":"telemetry","data":{"deviceId":"...","homieDeviceId":"...","property":"temperature","value":"...","timestamp":"..."}}`. |

Отдельный Actuator endpoint `GET /actuator/health` включён для Docker healthcheck; публично доступен только health endpoint. В текущем Compose порт 8081/8082 опубликован на интерфейсы Docker-хоста. Для не-доверенной сети ограничьте bind address/firewall/reverse proxy.

### 3.3 ESP8266 web-конфигуратор

У прошивки не REST API общего назначения, а HTML форма:

| Метод | Путь | Поля/результат |
|---|---|---|
| `GET` | `/` | Отдаёт форму настройки Wi-Fi и MQTT. Парольные поля при отображении не подставляются в HTML. |
| `POST` | `/save` | `ssid` (обязателен, до 64 символов), `wifiPassword` (пустое значение означает оставить прежний пароль), `mqttHost` (до 128 символов), `mqttPort` (1–65535), `mqttUser`, `mqttPassword` (пустое значение означает оставить прежний пароль). Сохраняет настройки в LittleFS и перезапускает ESP. Некорректные параметры — HTTP 400, ошибка записи — HTTP 500. |

## 4. Поток телеметрии MQTT/Homie

Для firmware по умолчанию `HOMIE_DEVICE_ID=esp8266-temp-01`; его можно изменить build flag в `esp8266/platformio.ini`. Устройство публикует retained metadata на `homie/<deviceId>/...` для Homie Convention 4.0.0. Температура публикуется retained сообщением каждые 5 секунд по топику:

```text
homie/<deviceId>/sensor/temperature
```

Payload — строка с температурой в °C, формат `%.2f`; например `23.50`. Backend подписан на `homie/+/sensor/temperature`, игнорирует metadata, находит устройство по Homie ID, сохраняет последнее значение и посылает владельцу событие по WS. Чтобы связать датчик с аккаунтом, сначала создайте группу, затем добавьте устройство с `homieDeviceId`, равным firmware ID.

В текущей прошивке публикуются Homie метаданные `$homie`, `$name`, `$state`, `$nodes`, `$type`, `$properties`, `$datatype`, `$unit` и `$settable`; Last Will публикует `$state=lost`. Это облегчённая реализация, а не полная сертификация соответствия Homie. MQTT username/password необязательны только для локального dev broker; для production нужны TLS, отдельная аутентификация/ACL каждого устройства и provisioning.

## 5. ESP8266: системный datasheet

Это описание именно собранного прототипа в проекте; точная ревизия платы/модулей и допустимые значения питания должны быть подтверждены по маркировке и datasheet конкретных компонентов. Не воспринимайте таблицу как электрический datasheet производителя.

| Параметр | Реализация/значение |
|---|---|
| Контроллер/плата | ESP8266, PlatformIO environment `esp12e`, Arduino framework |
| Периферия температуры | LM75A, I²C, драйвер в `esp8266/lib/LM75A`; адрес драйвера по умолчанию `0x48`; шаг преобразования, указанный в локальном драйвере, `0.125 °C` |
| Отображение | 4-разрядный TM1637; яркость выставляется в 7 из доступного библиотеке диапазона |
| TM1637 CLK | GPIO5 / маркировка платы D1 |
| TM1637 DIO | GPIO4 / маркировка платы D2 |
| LM75A I²C | Используется глобальный `Wire` библиотеки; прошивка явно не вызывает `Wire.begin(...)`, значит применяется стандартная разводка I²C выбранной платы/core. Подтвердите SDA/SCL конкретной платы и при необходимости явно задайте Wire pins перед монтажом. |
| Wi-Fi | ESP8266 STA к сохранённой сети; при отсутствии настроек или неудаче подключения поднимается конфигурационная AP |
| MQTT | PubSubClient; host/port/user/password задаются через web UI; базовый порт — 1883; соединение не TLS в текущей реализации |
| Web config | `ESP8266WebServer` на TCP 80, AP IP `192.168.4.1` |
| Хранение настроек | LittleFS, файл `/settings.ini`, plaintext (пароли не шифруются) |
| Температура для отправки | Публикуется при `−100 < T < 150 °C`; backend дополнительно принимает для свойства temperature только допустимое число в диапазоне −100…200 °C |
| Интервал публикации | 5 секунд, retained MQTT payload |
| Serial | 115200 baud |
| Setup AP | SSID `SmartHome-Setup`, пароль по умолчанию `setup1234` |

### 5.1 Подключение прототипа

Подключите TM1637 CLK к D1/GPIO5, DIO к D2/GPIO4, а питание/землю — по документации конкретного дисплейного модуля. LM75A подключите к питанию, GND, SDA и SCL шине выбранной ESP8266-платы; I²C адрес по умолчанию драйвера `0x48` зависит также от выводов выбора адреса датчика. Уровни сигналов и напряжение питания должны соответствовать модулю и логике ESP8266; GPIO ESP8266 не следует считать 5-вольт tolerant. До включения проверьте pinout, питание и наличие подтягивающих резисторов SDA/SCL на модулях.

Из-за отсутствия явного `Wire.begin()` и подтверждённой ревизии платы необходимо сверить SDA/SCL mapping с выбранной платой ESP-12E/NodeMCU и установить его явно в прошивке, если wiring отличается от default core mapping. TM1637 использует GPIO 4 и 5 независимо от I²C драйвера, однако нельзя считать произвольную плату безопасной без проверки полного pinout/boot-strapping pins.

## 6. Руководство по веб-приложению ESP8266

### Первичная настройка

1. Прошейте плату PlatformIO-командами `pio run`, затем `pio run --target upload`. Для диагностического вывода используйте `pio device monitor` (115200 baud).
2. При первом старте без сохранённого SSID устройство поднимет Wi-Fi сеть `SmartHome-Setup` с временным паролем `setup1234` и выведет AP IP в Serial (обычно `192.168.4.1`).
3. Подключите телефон/компьютер к этой сети и откройте `http://192.168.4.1/`. У мобильного клиента отдельного WebView-пункта настройки в текущем UI нет; конфигурацию выполняют системным браузером.
4. Заполните Wi-Fi SSID и пароль, затем MQTT host. Для Compose на компьютере укажите LAN IP компьютера, например `192.168.1.10`, а не `localhost` и не `mosquitto` (эти имена не разрешаются в сети ESP). Укажите порт, обычно `1883`; если брокер требует credentials, заполните username/password.
5. Нажмите «Сохранить и перезапустить». Прошивка проверит базовые пределы полей, запишет настройки в LittleFS, отправит ответ и перезапустится.
6. Если подключение к Wi-Fi удалось, Serial выведет выданный роутером IP. Откройте `http://<этот-IP>/`, чтобы снова попасть в конфигуратор. Телефон и ESP должны находиться в одной LAN/VLAN с разрешённым доступом.
7. В приложении создайте группу и добавьте устройство с Homie ID `esp8266-temp-01` (либо со значением, которым прошивка была собрана). При наличии публикаций текущая температура появится в карточке устройства.

### Изменение сохранённой конфигурации

Откройте web UI по LAN адресу устройства. При замене Wi-Fi или MQTT пароля оставьте соответствующее поле пароля пустым, если нужно сохранить прежнее значение; чтобы заменить — введите новый пароль. В форме SSID требуется заполнить заново. После сохранения устройство перезапустится.

### Восстановление доступа и диагностика

Если Wi-Fi не подключается в течение примерно 20 секунд, прошивка включает setup AP. Подключитесь к `SmartHome-Setup` и исправьте SSID/password. Если AP не появляется, откройте Serial monitor на 115200 и перезапустите плату. Если форма доступна, но телеметрия не приходит, проверьте доступность брокера из Wi-Fi сегмента ESP, host/port, MQTT credentials, Homie ID, питание/проводку LM75A, а также регистрацию устройства с тем же ID. Список DHCP клиентов роутера поможет найти LAN IP ESP.

### Ограничения и безопасность

Настроечная точка доступа использует жёстко заданный общий пароль и локальный HTTP без TLS или отдельной аутентификации веб-страницы. Конфигурационные Wi-Fi/MQTT пароли хранятся в LittleFS незашифрованными. MQTT соединение не защищено TLS, а dev Mosquitto разрешает anonymous подключения. Не подключайте такой стенд к недоверенной/публичной сети и не используйте реальные секреты. Перед production нужны уникальная безопасная процедура provisioning, аутентификация UI, защищённый канал управления, зашифрованное/защищённое хранение, MQTT TLS и per-device ACL.

На текущей прошивке нет отдельного WebView интегрированного в Android UI, удалённого provisioning, captive portal, OTA, полноценного Homie lifecycle/discovery, MQTT TLS, MQTT command subscription или обновления конфигурации по API. Нет и явной проверки достоверности адреса брокера/сертификата. Это следует считать прототипом стенда.

## 7. Сверка и известные расхождения

В мобильном UI существует переход регистрации к подтверждению кода, однако backend работает только с `REQUIRE_EMAIL_CONFIRMATION=false` по умолчанию и при этом `/auth/confirm` вернёт `404`; фактический happy path — регистрация без подтверждения → вход. Кнопка logout пока очищает только локальный токен. Группа добавляется/выбирается, но UI не предоставляет удаление группы. Команда `target-temperature` предусмотрена API, но термометр не имеет исполнительного выхода. Датчик регистрируется вручную по Homie ID; криптографического pairing/provisioning нет. Полная компиляция backend, Android и firmware зависит от наличия Maven/Gradle/PlatformIO/Docker toolchain; в текущей среде сборки не подтверждены.
